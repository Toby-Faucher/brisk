# Stage 1 API contract: game ids, caps, compat

Status: built and merged to main (through `stack-all`, PR #13). The web half implements the client side of this file.
Context: `docs/plans/2026-10-28-emulator-roadmap.md` (Stage 1). Fixtures to read:
`crates/brisk-hostd/tests/fixtures/stage1/` (`games-old.json`, `games-new.json`, `old-data/`, `new-data/`).

The rule for the whole stage: a new hostd answers old and new clients, so the hub UI can talk to a fleet where
hostds run different versions. bawn keeps the old hostd until Toby says otherwise.

## 1. Ids

A game id is a string.

- Steam: `steam:<appid>`, for example `steam:620`. The number has no leading zeros (`steam:0620` is refused).
- Emulator: `emu:<emulator>:<id>`, for example `emu:dolphin:mario-kart-wii`. `<emulator>` is lowercase
  letters and digits (`dolphin`). `<id>` is 1 to 64 characters of `A-Za-z0-9._~-`. The `<id>` is stored in the
  machine's library record (`library.json`), not computed from the name at request time.
- Today the `<id>` is a slug of the game name, made once at migration (`mario-kart-wii`). A second game with
  the same slug gets `~2`, then `~3`. A later stage may replace it with the disc id (`RMCE01`). The record then
  keeps the old id as an alias, and hostd answers the alias with the new id. Do not parse the `<id>` part.
- Treat an id as opaque text. Branch on `game.source` and `game.caps`, never on the shape of the id and never
  on the number range.

In URLs the id goes in one path segment. The colon may be plain or encoded: `/api/games/steam:620/local` and
`/api/games/steam%3A620/local` are the same request. Use `encodeURIComponent(id)` once.

## 2. The game object

`GET /api/games` answers `{games: [Game], ownedAvailable, idScheme}`. `idScheme: 1` says this hostd knows the
string ids. An older hostd leaves it out.

New fields on every game:

| Field | Type | Meaning |
|---|---|---|
| `id` | string | The id above. The key to use everywhere. |
| `source` | `"steam"` or `"emu"` | Who owns the game. |
| `caps` | object | What the source can do with this game (below). |
| `legacyId` | string | The old number as text. Steam: the appid. Emulator: the old `0xE0000000`+ hash. For one release. |
| `system` | string, only when known | `"wii"`, `"gamecube"`. Absent for Steam, and absent until a later stage fills it. |

Fields that stay as they were: `appid` (number), `name`, `installed`, `sizeBytes`, `lastPlayed`, `playtimeMin`,
`playtime2wkMin`, `cover`, `hero`, `logo`, `running`, `achUnlocked`, `achTotal`, `updated`, `update`,
`controller`, `coop`, and `emulator` (only on emulator games, `"dolphin"`, the system badge on the card).

`appid` is kept so an older web build keeps working. For a Steam game it is the Steam appid. For an emulator game
it is the old hash, the same number the first emulator version used, so it is not a Steam appid. Do not use it
as a key in new code. `appid` and `legacyId` go away after one release.

`caps` (all booleans): `install`, `controls`, `achievements`, `launchOptions`, `saves`, `screenshots`.

| Source | install | controls | achievements | launchOptions | saves | screenshots |
|---|---|---|---|---|---|---|
| Steam | true | false | true | true | false | true |
| Emulator with an editor (Dolphin) | false | true | false | true | false | false |
| Emulator without an editor | false | false | false | true | false | false |

`saves` is false for everything until Stage 6. `launchOptions` is true for every game since Stage 4. `controls` means the Emulator
mappings editor applies to this game's emulator. Show Install only if `caps.install`, Controls only if
`caps.controls`, and so on. There is no other emulator test.

## 3. Compat rules (what hostd accepts)

Everywhere a request names a game:

1. The new string id is accepted.
2. A bare number is accepted. It means Steam (`620` is `steam:620`), unless it is 3758096384 or more. Then it
   is an old emulator number, and hostd looks it up in this machine's library (`legacyId`). Not found is an
   unknown game.
3. A string with another shape is a bad id.

Where the id sits:

| Request | How to name the game |
|---|---|
| `POST /api/launch`, `/api/install`, `/api/quit` | body `{"id": "steam:620"}`. Also accepted: `{"id": 620}`, `{"id": "620"}`, and the old `{"appid": 620}` (a JSON number only; `"620"` in `appid` is a 400). If both are sent, `id` wins. `quit` also takes `"force": true`. |
| `POST /api/stream` | same two fields, next to `preset` and the rest. Omit both for the Desktop or a quality change. |
| `GET /api/games/{id}/info`, `/achievements`, `/news`, `/local`, `/screenshots/{name}` | path segment |
| `PUT /api/notes/games/{id}` | path segment |
| `PUT` and `DELETE /api/prefs/{id}` | path segment |

Status codes:

- Path routes: 400 for text that is no id (`nope`, `steam:0620`, `emu:dolphin`). 404 for a good id, or a bare
  number, that this machine does not have. `/info`, `/achievements` and `/news` are 404 for an emulator game
  (`no Steam details for this game`), as before.
- Body routes: 400 for a bad or unknown id (`unknown game`), and 400 when neither `id` nor `appid` is sent.
  Same as before for the old numeric form.
- `POST /api/install` on a game with `caps.install` false: 400 `nothing to install for this game`.
- Notes and prefs accept any well-formed id, known or not (400 only for a bad one). A bare number of
  3758096384 or more with no library match is a 400 there too.
- `POST /api/quit`: unchanged answers (`closed` or `still-running`, 409 for not running or already quitting,
  the 25 s limit).

Unchanged routes: `GET /api/emulators/dolphin/controls/{kind}`, `PUT` the same, `POST .../reset`. They take
no game id. They answer 404 `no controls on this machine` unless the library has a game whose emulator has an
editor.

Responses that carry a game id:

- `GET /api/stream` and the `POST /api/stream` answer gain `gameId` next to `appid`. Both are null for the Desktop.
- `GET /api/sessions` rows and `GET /api/sessions/{started}` gain `gameId`, next to `appid`. Older rows that
  hostd rewrote at startup have it too. A Desktop row has neither.
- `GET /api/notes`: `games` is keyed by id (`steam:620`).
- `GET /api/prefs`: `prefs` is keyed by id.

## 4. A mixed fleet, from the web client's side

Two kinds of hostd answer, and the web app should handle both until the old one is gone.

- Old hostd: `GET /api/games` has no `idScheme`, no `id`, no `caps`. Games are keyed by number. Routes take only
  numbers: `/api/games/620/info`, body `{"appid": 620}`.
- New hostd: everything above.

Suggested client behaviour:

1. Build the client's game key as `game.id ?? String(game.appid)`. Machine id plus that key is unique.
2. Per machine, decide the request form from that machine's own `/api/m/{machine}/games` answer. If its games
   have `id` (or `idScheme` is 1), put the id in paths and bodies. If not, put the number: `String(appid)` in
   paths and `{"appid": n}` in bodies. A new id sent to an old hostd is a 400.
3. The old numeric form also works against a new hostd (rule 2 above), so a client that is unsure may send
   numbers to everything for one release. It will not work once `appid` and `legacyId` go away.
4. Caps for an old hostd: it sends none. Derive them from the old test: a game with `emulator` set has
   `controls` true and `install` false, every other game has `install` true and `achievements` true.
5. Notes and prefs live on the hub, so their key form depends on the hub's hostd, which can differ from the
   machine's. Ask the hub's own `/api/games` (or `/api/notes` after a write) for `idScheme`. Read a game's note
   with `notes.games[id] ?? notes.games[legacyId]` (the second for a hub that is still old, or an emulator entry
   not remapped yet). Write with the id form only when the hub is new, else with the number.
6. Emulator games on a hub: the hub has no library, so startup could not rekey notes and prefs that were stored
   under an emulator's old number. They stay under the old number. When a machine's games arrive with
   `legacyId` and `id` for an emulator game, and the hub has `notes.games[legacyId]` or `prefs[legacyId]`, send
   `POST /api/ids/remap` on the hub with `{"map": {"3907440760": "emu:dolphin:mario-kart-wii"}}`. It answers
   `{"notes": n, "prefs": m}` (how many entries moved), is safe to repeat, copies the file to `<file>.pre-ids`
   before the first change, and never overwrites an entry that already has the new key. Keys must be old
   emulator numbers and values must be `emu:` ids, else 400. At most 2000 pairs. Skip the call when the hub is
   an old hostd (it has no such route).

## 5. The library file (emulator games)

`data_dir/library.json`: `{"v": 1, "games": [Record]}`. A record:

```
{"id": "emu:dolphin:mario-kart-wii", "emulator": "dolphin", "name": "Mario Kart Wii",
 "file": "/path/to/game.iso", "source": "manual", "legacyId": 3907440760}
```

Optional: `system`, `addedAt`, `aliases` (ids this game had before). Unknown fields are ignored. A record whose
id is not an `emu:<its emulator>:...` id is skipped with a warning. Hand editing is the only way to add a game
until Stage 2 (the add and remove routes). Remove will forget the record and keep the file.

The emulators come from a static table in `registry.rs` (command, arguments, window class, controller types,
systems, extensions). Dolphin is the one row.

## 6. Migration

Runs at hostd start, before it accepts requests, in `main.rs` (`migrate::run`). The conversions are pure
functions in `migrate.rs` with fixture tests. Each file step:

- A file that is missing is skipped. A file that does not parse is left alone with a warning, and the other
  files still migrate.
- An unchanged result writes nothing. A second start changes nothing.
- Before the first rewrite the original is copied to `<file>.pre-ids`. The copy is made once and never
  replaced, even if a later start rewrites the file again.
- The new text goes to a temp file in the same directory (0600), is synced and renamed over the old file.
  A crash leaves the old file or the new one, never half of one.

What it does:

| File | Change |
|---|---|
| `emulators.json` | If `library.json` does not exist, write it from the old list. The old file is never changed or deleted. With `library.json` present, the old file is ignored. |
| `notes.json` | Keys of `games`: `620` becomes `steam:620`. An old emulator number becomes the library's id for it. |
| `prefs.json` | Same for the game keys. `layout` is untouched. |
| `sessions.jsonl` | A row with an `appid` and no `gameId` gets a `gameId`. `appid` stays. Desktop rows and lines that are not JSON stay as they are. |
| `emu-played.json` | Same key rule (last-played stamps). |

Key rule: a key that is already a new id stays. A number below 3758096384 becomes `steam:<n>`. A number from
there up becomes the library's id for that old hash. With no match it stays as it is and is listed in the log.
Nothing is dropped. If the new key already exists, the old entry stays under its old key and is logged.

Ids of the migrated emulator games come from the name: lowercase, anything but letters and digits becomes one
`-`, cut at 48 characters. A name with no ASCII letters becomes `g` plus the old hash in hex.

## 7. Rollback

An old hostd cannot read the new files: it drops string keys in `prefs.json` and reads a `notes.json` with
string keys as empty. So rolling hostd back means restoring the copies first:

1. Stop hostd.
2. For each of `notes.json`, `prefs.json`, `sessions.jsonl`, `emu-played.json`: move `<file>.pre-ids` over `<file>`.
   Anything written after the migration (new notes, new rows) is lost with it.
3. Start the old hostd. It reads `emulators.json`, which was never touched, and ignores `library.json`.

`library.json` and the `.pre-ids` copies can stay on disk. Migrating again later is safe: the copies are only
made if they are missing, so delete the `.pre-ids` file after a rollback if you want a fresh copy next time.

## 8. What the web half must do

1. `Game.id: string`, plus `source`, `caps`, `legacyId`, `system?`. Keep `appid` typed for the old hostd.
2. One helper for the key and for URLs: `gameKey(g) = g.id ?? String(g.appid)`, `gameUrl(g, tail)` with
   `encodeURIComponent` once. Bodies send `{id}` for a new hostd and `{appid}` for an old one.
3. Replace every "is this an emulator" test with `caps` (and `source` for the badge). Old hostd games get caps
   from the rule in section 4.
4. Notes, tags and prefs: read both key forms, write the form the hub speaks. Call `POST /api/ids/remap` on the
   hub as described in section 4.
5. Session rows and stream info: show by `gameId ?? appid`.
6. Tests and fixtures: use `tests/fixtures/stage1/games-old.json` and `games-new.json` as the two shapes, and
   cover a machine of each kind in one session.

Not in this stage: launch options, uploads and the games folder (`~/Games`), the playtime watcher, header based
ids, metadata and art, and the add and remove routes for the library.
