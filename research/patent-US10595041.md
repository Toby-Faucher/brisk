## Abstract (paraphrase, not verbatim)
Client uses lookup tables from server to match user input to motion vectors, tags and sums them, applies them to decoded frames. Other embodiments: server caches repetitive motion vectors as a library the client stores and updates from user input, so motion starts before the server's actual video arrives.

## Independent claims (2: claim 1 method, claim 11 system). Fetched in short segments, order preserved; punctuation/joins approximate.
Claim 1: "A computer-implemented method for caching motion vectors comprising: transmitting a previously generated motion vector library from a server to a client, wherein the motion vector library is configured to be stored at the client; transmitting an instruction to the client to monitor for input data from a user; transmitting an instruction to the client to calculate a motion estimate from the input data; and transmitting an instruction to the client to update the stored motion vector library wherein the client applies the stored motion vector library to initiate motion in a graphic interface prior to receiving actual motion vector data from the server."

Claim 11: same, as "A system for caching motion vectors, wherein, over a network, a server: transmits ... [identical elements]".

## Element chart vs C17
| Claim 1 element | C17 | Note |
|---|---|---|
| Server transmits previously generated MV library to client | AVOIDS | C17 has no server-supplied library; client learns itself, no game/server cooperation |
| Library stored at client | partial | C17 stores a learned model, not a server-sent MV library |
| Server instructs client to monitor user input | AVOIDS | C17 client acts on its own; no server instruction |

| Server instructs client to update stored library | AVOIDS (instruction); "update" resembles online learning | |
| Client applies library to initiate motion before actual MVs from server | different mechanism | C17 warps latest decoded frame, not codec macroblock MVs |
Because every claim requires "transmitting ... from a server" a library and instructions, C17 (client-only, no server cooperation) misses multiple elements of both independent claims. Every dependent claim inherits this.

## Specific questions
- Learned / online-fit input->motion mapping claimed? NO. Library is "previously generated" by server (game-generated, build-time per dep. claims 6, 8). The client "updates" it from user input, but no system identification from measured global motion in decoded video is claimed. Description (read in part) describes lookup tables of server-supplied vectors and correction vectors (actual minus estimated).
- Applied to decoded frames client-side? Description/abstract: yes, motion estimate applied client-side (shifting macroblocks of the next frame), with tag matching to retire the estimate when the server's tagged frame arrives. Not claimed as a rotational warp/reprojection of the latest frame; description frames it as macroblock shifting. View rotation is named as a good use case ("consistent motion vectors, such as player view rotations") so conceptual overlap on the goal is real.
- Needs game hooks? The described scheme needs server/game-side vector generation, i.e. it is not for unmodified games.

## Novelty / FTO read (non-lawyer)
1. Granted claims 1/11 look easy to avoid for a client-only, no-server-cooperation design: no server-sent library, no server instructions.
2. Does it kill C17 novelty? Not the core: learned mapping from measured global motion + rotational reprojection of decoded frame is not disclosed in what I read. But the *goal* (client-side latency hiding for view rotation from input, before server response) is prior art in this family, so frame C17 on the mechanism (no hooks, online identification, reprojection), not the goal.
3. Risk: continuations (US16/716,731, 17/227,804, 18/141,698, 19/004,094; and cited-by US11503332/11601670/11695951/12219171) may have broader claims. NOT checked. Next step: read their claims.
4. Expiry ~2038-04-20 (estimate), so not a near-term clear.
